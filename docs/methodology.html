Methodology

The question, asked in the AA Mafia group on 2025-09-11: is there a dashboard that shows how much paymasters are actually used across L1 and L2s, as a percentage of all transactions? This page explains how the dashboard answers it, and where the answer stops.

Window and chains

  • Window: 2026-09-24 00:00 UTC to 2026-10-24 00:00 UTC, 30 full days, end exclusive. The end date is the last full day that growthepie had published when the data was pulled (2026-10-25).
  • Chains: Ethereum mainnet, Base, Arbitrum One, OP Mainnet, Polygon PoS.
  • The first and last block of the window on each chain are in docs/evidence/window-blocks.json, with the timestamps of the blocks on each side of the boundary.

Definitions

  • Userop: one UserOperationEvent from one of the four EntryPoints. Failed userops are included, because the paymaster still paid gas for them. The success flag is kept in the raw tables.
  • Paymaster-paid userop: a userop whose event has a nonzero paymaster field. Without a paymaster, the smart account paid its own gas from its EntryPoint deposit or balance.
  • Bundle: one transaction that contains one or more userops. A bundle is a real transaction on the chain, so bundles as a share of chain transactions is a true share. Userops are not transactions, so userops per 100 chain transactions is a ratio, not a share, and can pass 100 in theory.
  • Paymaster bundle: a bundle with at least one paymaster-paid userop.
  • ERC-20 mode userop: a paymaster-paid userop where the paymaster contract emitted one of the events below with the ERC-20 flag set. The user paid for gas in a token.
  • Stablecoin userop: an ERC-20 mode userop whose token address is listed in data/stablecoins.csv.
  • Paymaster, no ERC-20 event: every other paymaster-paid userop. Most of these are sponsored (the app or provider paid). This group is an upper bound on sponsorship, because an ERC-20 paymaster that emits none of the events below lands here too.

How sponsored and ERC-20 userops are told apart

First, a sample of full bundle transactions on each chain showed which events each paymaster contract emits in the same transaction as its userops (scripts/sample_fee_transfers.py, output in data/raw/paymaster-emitted-events-sample-*.csv). An event only counts when the contract that emitted it is a paymaster that appears in UserOperationEvent on that chain in the window. Counts are per event over the window. The samples show one event per userop for these contracts.

One more rule uses labels instead of events. A paymaster whose sourced label says it is ERC-20 only (for example UXLink and Bron), and that emits none of the events above, has all its userops counted as ERC-20 mode with the token shown as unknown. Those userops are never counted as stablecoin, because the token is not visible in the logs.

A first attempt matched ERC-20 Transfer logs from the userop sender. It does not work: most such transfers are the user's own payments to apps, not gas fees. That sample is kept in data/raw/fee-transfer-sample-*.csv as evidence.

Known gaps

  • ERC-20 share is a lower bound. Paymasters that charge a token but emit none of the events above count as "no ERC-20 event". The main known case is Stackup, whose paymaster can run both modes and emits no per-userop event. Its mode sits only in paymasterAndData, which is calldata and is not read here. Hybrid contracts with no event, and unlabeled contracts, all land in "no ERC-20 event".
  • Sponsorship without a paymaster is missed. Gelato Gas Tank and Alchemy bundler-sponsored userops set no paymaster and look like self-paid userops.
  • Only canonical ERC-4337. Non-canonical EntryPoints, native account abstraction (zkSync, Starknet) and EIP-7702 accounts that send normal transactions without an EntryPoint are not counted.
  • Chain totals use growthepie's definition. L2BEAT agrees within 0.2% on the L2s where both exist. L2BEAT has no Ethereum or Polygon PoS series here, so those two have one source only.
  • Some labels are weak. About 20 labels rest only on BundleBear or Pimlico's 4337-stats file, and a few rest only on a verified contract name. Each row says which in its note. Eight labeled addresses have no known operator, including the largest paymaster on Polygon PoS.
  • Labels cover the top paymasters only. The table lists the top 25 per chain. Unlabeled means no public source was found, not that the contract is unknown to everyone.
  • Stablecoin list is short. Only USDC, EURC, USDT and USDT0 addresses with an issuer page are counted as stablecoins. DAI, USAT, bridged USDC (USDC.e) and the older bridged USDT on OP Mainnet (0x94b0...8e58) appear in the token table with small counts and are not counted, so the stablecoin share is slightly low.
  • No USD values. Gas cost is kept in native units (actual_gas_cost_wei) in the raw tables. It is not converted to USD.
  • One window. The numbers describe these 30 days only. They are not a trend.

Reproduce

python3 scripts/find_window_blocks.py
python3 scripts/fetch_chain_txcounts.py
for c in ethereum base arbitrum optimism polygon; do
  python3 scripts/extract_userops.py $c 4
  python3 scripts/aggregate_userops.py $c
  python3 scripts/extract_paymaster_mode_events.py $c 2
done
python3 scripts/resolve_tokens.py
python3 scripts/summarize.py
python3 scripts/build_dashboard.py

Python 3 standard library only. The per-userop work files are too large to commit (data/work/ is git-ignored). Their SHA-256 hashes are in docs/evidence/work-file-*.json, and the hash of every portal response is in docs/evidence/portal-responses-*.csv. Run logs are in docs/evidence/run-*.log.
